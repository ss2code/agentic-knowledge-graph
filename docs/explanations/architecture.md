# Architecture Overview: Agentic Knowledge Graph Builder

## Overview
The Agentic Knowledge Graph Builder is a system for building, refining, and visualizing Knowledge Graphs from structured and unstructured data using LLM agents and Neo4j. It manages isolated "Context" directories to process distinct datasets independently without cross-contamination.

## Architecture & Role
The project follows an orchestrator-agent pattern, segmented into four primary layers:
1. **Orchestrator** (`orchestrator.py`): The central controller that manages the interactive CLI loop and coordinates the execution of agents.
2. **Context & State Management** (`core/context.py`, `state_manager.py`): Isolates project data (user inputs, Neo4j DB, outputs) and persists pipeline execution state in `system_state.json`.
3. **Agents** (`agents/`): Task-specific LLM workers (Intent, Schema, Extraction, Graph Builder, Pipeline, Visualizer, TextToCypher) that interact sequentially to refine schemas and build the graph.
4. **Services** (`services/`): Wrappers around external infrastructure — Neo4j (`graph_service.py`), Docker container management (`container_service.py`), LLM provider abstraction (`llm_provider.py`), and Anthropic/sentence-transformer adapters for GraphRAG (`anthropic_graphrag.py`).

## Data Flow
Data moves linearly through the pipeline, coordinated by the `Orchestrator`:
Raw files in `<context>/user_data/` ➔ **IntentAgent** defines goals (`user_intent.json`) ➔ **SchemaAgent** generates/negotiates (`construction_plan.json`) ➔ **ExtractionAgent** creates extraction logic ➔ **GraphBuilderAgent** populates DB ➔ **KgPipelineAgent** runs knowledge discovery (GraphRAG) ➔ Output is stored in **Neo4j** and exported to `.graphml`.

## Data Structures
- `Context`: Encapsulates paths for the user dataset (`base_path`, `user_data`, `neo4j_home`, `output`).
- `system_state.json`: Tracks flags (`intent_defined`, `files_approved`) and lifecycle status (`schema_status`, `graph_status`, `graphrag_status`).
- `user_intent.json`: Stores the domain and extraction goals generated by the IntentAgent.
- `construction_plan.json`: The negotiated Neo4j node/edge schema and extraction mapping constraints.

## Events & Signals
The codebase does not use a traditional event emitter. Instead, state transitions are imperative. The `StateManager` serves as a pseudo signal bus by managing cascading state invalidation; for example, calling `mark_intent_updated()` sets downstream states (`schema_status`, `graph_status`) to `"STALE"`, orchestrating what actions are allowable next.

## Input / Output
- **Input**: User-provided raw files (CSV, TXT, MD) placed in the `<context>/user_data/` directory.
- **Output**:
  - Live Neo4j database running in an isolated Docker container mapped to `<context>/neo4j_home/`.
  - Static exports: data dumps (`.graphml`) and visualization reports stored in `<context>/output/`.

## Key Functions & Classes
- `Orchestrator.main_loop()`: The central interactive terminal loop prompting the user through the pipeline steps.
- `StateManager.mark_intent_updated()`: Invalidates downstream graph and schema state when user goals naturally change.
- `KgPipelineAgent.run_knowledge_discovery()`: Executes the GraphRAG pipeline to find entities/connections in unstructured text.
- `ContainerService.start_neo4j_container()`: Dynamically provisions isolated Neo4j instances tailored to specific contexts.

## Dependencies
- **External APIs**: Anthropic (via `anthropic` SDK) providing agent reasoning. Models: `claude-haiku-4-5-20251001` (default, fast) and `claude-sonnet-4-6` (balanced). Set `PROJECT_ANTHROPIC_API_KEY`; agents fall back to simulation mode if unset.
- **Embeddings**: `sentence-transformers` (`all-MiniLM-L6-v2`) for local embeddings in the GraphRAG pipeline — no external embedding API required.
- **Infrastructure**: Docker Desktop is required for dynamically spinning up Neo4j instances.
- **Libraries**: Neo4j Python drivers, `neo4j-graphrag`, `streamlit`, `json-repair`.

## Notes
- **Design Decision**: Contexts are cleanly separated via directories, ensuring that different domains or datasets do not interfere with one another.
- **Gotcha**: Multiple contexts cannot run their Neo4j containers simultaneously because they attempt to bind to the same default Docker ports (`7474`, `7687`).
- **Testing**: End-to-end tests (`tests/run_e2e.py`) execute a simulated pipeline run. Neo4j must not be running on test ports prior to execution to avoid port conflicts.
